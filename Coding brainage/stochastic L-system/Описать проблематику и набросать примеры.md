Дерево состоит из нескольких типов соединительных узлов.
Между узлами одного типа обязательно есть слой узлов второго типа.

```text
 .
├── part 1/
│   ├── design version 1
│   ├── design version 2/
│   │   ├── part 2/
│   │   │   ├── design version 4
│   │   │   └── design version 5
│   │   └── part 3/
│   │       ├── design version 6/
│   │       │   ├── part 4
│   │       │   └── part6
│   │       └── design version 7
│   └── design version 3
└── part 7
```

простейший набор правил со стохастикой
```
part -> design version (x1..100)
design version -> part (x 0..100)
```

пример эволюции
```
1) в корне изделие
part

2) сгенерировалось несколько версий
part
	dv
	dv
	dv

3) у версий сгенерировалось от 0 до нескольких партов
part
	dv
		part
		part
	dv
	dv
		part
```

на самом деле наличие у изделий версий и у версий изделий связано с кучей других бизнесовых параметров:
- если у изделия несколько версий, значит, у них разные значения аттрибута "статус"
- если у версии есть изделия потомки, значит оно кастомное и помечено как сборка
- если у изделия нет потомков, значит оно может быть не только кастомным, но и покупным или стандартным
- если изделие кастомное и не имеет потомков, значит, у него может быть указан материал - ссылка на покупное изделие
- если изделие покупное, у него может быть несколько совместимых артикулов

Есть ощущение, что рост дерева должен происходить в два тика:
- из текущей формы дерева применяем стохастические правила по раскарске (то есть, расстановке зависимых атрибутов)
	- в том числе, является ли уровень последним и надо ли в связи с этим предпринять какие-то last-minute обновления типа смены типа с custom на procured или 
- из расставленных атрибутов применяем стохастические правила по генерации следующего уровня

форма определяет набор правил для генерации аттрибутов, аттрибуты влияют на форму

Отсюда получаются уточнения для генерации следующего поколения:
```
part ->
	part & custom
	part & procured
	part & standard

part & procured
	part.procured_sku[0]
	part.procured_sku[1]
	...
	part.procured_sku[5]

part & custom ->
	part.dv[0]
	part.dv[1]
	part.dv[2]
	...
	part.dv[10]

dv ->
	dv & production | prototype | declined

dv & production | prototype | declined ->
	dv & is_assmebly
	dv & has_material

dv & is_assembly ->
	dv_spec.part

```

получились разные виды переходов и свойств
- переход, который добавляет свойства
- переход, который добавляет новую связь и новую сущность
- свойство может ограничивать переход
- свойство может не накладывать существенных ограничений

у свойства может быть несколько значений, которые не влияют на последующий переход

что тут переменная, а что константа?

Итого:
получился код, который работает в следующим образом:
1. проходимся по "поверхности" дерева
2. собираем для каждого узла запускаем его функцию эволюции, отвязываясь от реализации
3. узел возвращает своих детей или себя (включается в новую поверхность)
	- можно кстт предусмотреть вариант, что он не возвращает себя, чтобы дальше не расти
4. все новые дети формируют в итоге итерации новую поверхность
5. повторяем с новой поверхностью все пункты выше

Подробнее про пункт 2
- свойства узла определяют форму потомства (у кастомного изделия могут быть версии, у остальных видов изделий - нет)
- одна итерация эволюции узла состоит из двух пунктов:
	- выбрать наугад себе свойства
	- выбрать наугад себе развитие потомства в зависимости от свойств

Похоже что у узлов сформировался примерный интерфейс.
