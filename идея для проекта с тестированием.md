(Из чатика CTX-dev; мотивация) Мысли о тестописании:  
- создавать для каждого компонента объект, имплементирующий интерфейс `IFSMTest` (на первом скрине `FSMTestSetup`)  
- внутри него сохранять дефолтное состояние данных, пробрасываемых в компонент, и соответствующей дефолтному состоянию спеки  
- методами из интерфейса тонко настраивать данные и спеку для групп тестов  
  
ps: builder-pattern помогает совмещать куски конфигов из разных тестов, например, когда нужно прикрутить уже готовую фичу на страницу, где её раньше не было, можно сетап тестов этой фичи переиспользовать бл-ря такому способу сборки.  
  
а еще такой подход пердполагает что-то типа стандартизации для функций-генераторов, которые нужно писать для разных групп тестов и которые сами собой получаются очень разные (потому что пилятся под разные сценарии работы компонента).  
В данном случае они будут читаться +- одинаково и устроены из одних и тех же "примитивов":  
- обновить конкретный узел в дереве данных (для запроса или для пропов)  
- обновить спеку конкретного элемента  
- добавить конкретное действие в transition (click/toggle/select/input)
